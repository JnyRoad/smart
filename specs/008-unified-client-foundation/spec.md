# Feature Specification: 裕慧家园统一客户端骨架

**Feature Branch**: `feat/uniapp-x-foundation`
**Created**: 2026-09-05
**Status**: 骨架、自适应封条标签、现场实时搜索、厂牌完整资料、设置选岗前置及押运方式核验已通过本地演示验收；真实集成待联调
**Input**: 用户确认以 uni-app x 蒸汽模式搭建 smart-app，保密物品放行在 App 内申请、审批和现场执行；供应商通行在入厂时申请，App 仅扫码核验及登记进出；支持 DHR 员工、外包与派遣人员；移动、Web、小程序复用优先，鸿蒙按适配成本安排。

## User Scenarios & Testing

### User Story 1 - 同一入口登录与权限工作台 (Priority: P1)
人员输入工号和密码，系统以服务端身份和权限显示业务入口；岗位仅在执行需要时选择。
**Independent Test**: 使用三类身份契约验证登录；未知身份、缺失权限和会话过期均不能获得业务权限。
**Acceptance Scenarios**:
1. 正式、外包、派遣身份采用同一登录表单，身份类型由服务端决定，用户不能自行选择生产身份或角色。
2. 只有授权的入口可见；通过直接路由进入未授权页面仍被拦截；未知模块不执行远程下发的任意 URL。
3. 会话过期或退出后清除身份、权限和岗位上下文；服务失败不能自动切换到演示数据。

### User Story 2 - 可扩展工作台 (Priority: P1)
四个稳定页签为工作台、待办、消息、我的。首页常用入口不超过八个，全部应用支持分类和搜索，个人常用列表受当前权限约束。
**Independent Test**: 同一模块注册结构加入多个入口后，首页仍保持固定规模；收藏与搜索不能暴露未授权模块。
**Acceptance Scenarios**: 无授权显示解释；待办和消息有加载、空、失败状态；手机与宽屏均能使用。

### User Story 3 - 两项首期业务的客户端流程 (Priority: P1)
保密物品放行提供申请、审批、记录和现场执行入口；供应商的保密区资格在入厂申请中完成，App 仅扫描已打印厂牌二维码，验证通过后由操作人明确选择进入或离开，查询独立进出事件。
**Independent Test**: 隔离演示中物品可完成提交、审批和执行；供应商可凭有效演示厂牌核验并登记进入、离开；真实模式只消费已配置契约，缺少接口时明确报错。
**Acceptance Scenarios**: 申请字段校验；审批权限与执行权限分开；出发/到达和进入/离开按状态提供操作；岗位必须属于当前身份授权范围。涉及强制人卡核验的真实放行不能用扫码或演示按钮替代。

### User Story 4 - 硬件与相机扫码 (Priority: P1)
在“我的 → 设置”选择硬件扫码头或摄像头并保存，所有扫码页只使用已保存方式，不再临时切换；硬件负责按键扫描、解码并输入当前编辑框。
**Independent Test**: 完整结束符、无结束符确认、前导零、重复扫描、异常和取消均有明确处理。
**Acceptance Scenarios**: 扫码输入框及现场搜索框管理对应焦点；封条添加和供应商核验仅处理完整结果，现场搜索则按输入实时筛选已加载单据；两种扫码来源进入相同解析逻辑；模式偏好持久保存在设备本地，重启及更换账号后继续使用；保存失败不改变已生效配置；浏览器相机能力未适配时如实显示不可用。

### Edge Cases
- 重复工号、离职或过期外包身份、主管缺失、权限回收、跨园区岗位、并发提交、超时后结果不确定。
- 扫码含超长文本或换行、连续重复扫码、相机拒绝权限、无硬件扫码头、后端业务拒绝。
- 演示身份和真实会话必须隔离，示例记录不能混入真实操作；用户权限不能由本地存储恢复。

## Requirements
### Functional Requirements
- **FR-001**: 基于用户创建的工程提供独立客户端目录及可复现验证方式。
- **FR-002**: 工号登录统一身份契约支持三类人员；密码不出现在 URL、日志、持久存储中。
- **FR-003**: 会话、请求错误、失效处理集中实现；真实模式失败不得伪造成功。
- **FR-004**: 模块、页面和按钮统一权限检查，服务端仍是最终授权方。
- **FR-005**: 四页签、最多八个常用入口、分类搜索和个人收藏。
- **FR-006**: 物品放行提供申请、审批、现场执行及记录；供应商仅提供厂牌核验、进出登记和记录；实际后端集成单独标明验收状态。
- **FR-007**: 硬件输入与摄像头扫码统一处理并支持设备偏好。
- **FR-008**: 岗位从授权集合选择，不能输入任意岗位获得执行权限。
- **FR-009**: 演示模式需显式进入并全程标识，数据仅模拟，绝不触发真实放行。
- **FR-010**: 复用真实裕同标志，界面采用品牌橙和清晰中文；生成插画有本地资源及来源记录。
- **FR-012**: 供应商不得出现 App 申请或审批入口，旧供应商申请/审批路由不得借默认值进入物品业务。二维码为不透明凭证，资格、有效期、区域及可执行方向由服务端验证，核验本身不写进出记录。岗位或身份切换、核验过期后须重新扫描；事件写入需再次授权并使用幂等键。
- **FR-013**: 外包和派遣在界面上统一为“外包／派遣人员”，同一身份与授权机制处理；保留服务端来源值以便数据兼容，不按来源自动授予不同角色。
- **FR-014**: 四个底部页签具有一致风格图标及文字；审批同意和驳回并排且间隔至少 10px，触控区域至少 44px；所有页面统一主次按钮、分组留白、空态/错误/加载反馈。
- **FR-011**: 未实现的真实 NFC、打印和小程序平台差异不得声称完成。

### Key Entities
- Identity：稳定人员标识、工号、人员来源、单位与授权。
- Session：认证凭据、有效期、身份；与设备偏好分离。
- Module：本地注册的业务入口、分类、权限和页面。
- Post：服务端授权的园区与岗位。
- Application：物品放行内容、申请人、状态、审批和执行轨迹。
- SupplierVerification：厂牌对应人员、单位、入厂授权、核验岗位、允许方向和短时有效期。
- SupplierPassage：单次进入/离开事件，含人员、单位、区域、岗位、操作人及时间。
- ScanResult：完整原始文本与输入来源。

## Success Criteria
- **SC-001**: 三类人员契约、拒绝访问、会话清理和重复操作均通过自动化测试。
- **SC-002**: 物品放行演示完成申请审批执行；供应商演示完成厂牌核验、进入、再次核验、离开与事件查询，未知/无效厂牌不得登记，真实/演示状态明确可辨。
- **SC-003**: 手机宽度和桌面宽度的登录、工作台、应用中心可用，常用入口不超过八个。
- **SC-004**: Web 编译和关键交互检查通过；原生编译、真机、小程序与后端集成分别记录结果或限制。

## Assumptions
- 本次交付是 4.1/4.2/4.3 客户端架构与首期业务页面骨架，不包含全系统后端重写或生产发布。
- 用户最新澄清：仅物品放行在 App 内申请与审批；供应商保密区资格来自入厂申请，覆盖首版将两类业务均建模为 App 申请的设计；工号登录零改造必须以源码核实，不能直接采信蓝图。
- 不连接生产、不执行 DDL/DML，不自动创建或授予正式账号权限。
- 真实业务尚缺契约或身份能力时提供明确的集成边界；演示不计为真实验收。

## 本轮验收补充
- 供应商历史记录按进入/离开事件展示，可按方向和人员/单位/厂牌检索，不显示“待审批”等申请状态。
- 扫描结果呈现人员、单位、授权区域、有效期、当前进出状态及核验反馈；进入/离开必须显式点击，不自动放行。
- 演示无效、过期、跨区域厂牌及重复操作必须拒绝；真实通行服务在事件提交时重新核验，客户端不定义真实通行资格。
- 移动、窄屏与宽屏检查主要页面，不出现按钮重叠、无间距、横向溢出或底部导航无图标。

### 本轮设置与岗位澄清
- **FR-015**：提供统一设置入口，扫码方式显式保存到设备持久存储；业务页无扫码头/摄像头切换控件，返回既有表单也同步新设置。
- **FR-016**：工作台顶部和“我的”不展示现场岗位选择。岗位仅用于有 item-pass:execute 或 supplier:execute 权限的安检操作，与 employee/outsourced/dispatched 来源无关。直接岗位路由和状态写入同样校验执行权限。
- **FR-017**：物品现场记录、扫码定位、执行详情及供应商核验页顶部只读显示当前岗位；岗位只能在设置内修改，岗位为空显示“请选择岗位”且禁用现场查询和扫码，人员变更清空岗位，申请人仅在申请表内填写出发/到达，不被要求绑定执行岗位。岗位选择保留在当前会话，不作为设备全局权限持久化。

### 连续扫码与安检核验补充
- **FR-018**：员工申请使用扫码头时回车自动添加封条，不显示“确认扫描内容”；已添加封条紧邻输入框上方，按扫描顺序追加到末尾，每枚有可触控的叉号删除按钮。数量增加时使用有高度上限的滚动区域，每次新增自动显示末尾条码，避免输入框被持续推远。每次成功添加后自动恢复输入焦点，支持连续扫描；重复、异常码不新增且仍可继续输入。
- **FR-019**：岗位修改只在设置页面完成并保存，业务页无切换入口。未选授权岗位时，现场物品执行列表、搜索、扫码定位及直链执行不得读取可执行单据或接受扫码。设置仅向有执行权限的人展示岗位项；换账号清空岗位。
- **FR-020**：供应商核验展示姓名、照片、公司、人员联系方式、被访人及其联系方式、授权起止时间、授权区域和厂牌/入厂单信息。照片缺失或失败时明确显示暂无照片，不以生成照片替代真实人员证件照；演示字段必须标示虚构。
- **FR-021**：物品出发执行必须明确选择押运人或定位锁。押运人必须完成刷卡核验；定位锁必须填写非空字符串编号并保留前导零。离开页面、换岗位或换账号不能沿用核验。执行参数由协调层再次校验，不能仅依赖按钮禁用。出发方式记录到单据，抵达沿用该方式重新核验；定位锁编号须与出发登记一致。真实刷卡及放行接口未接入时明确阻止真实执行。

### 封条标签与现场实时搜索
- **FR-022**：申请封条以随编号长度自适应的椭圆标签紧邻输入框上方排列，一行可容纳多个，空间不足自动换行；每枚可删除，长码不溢出，继续保留限高滚动和扫码后回焦。
- **FR-023**：物品现场执行页取消单独的“扫码定位单据”按钮，加载当前岗位可办理单据后，由搜索框按每次输入即时筛选单号、申请人、标题及封条，无需回车、不按字符请求后端。扫码头模式默认聚焦此搜索框，回车不跳页、不执行放行，下一次扫描可替换上次编号；摄像头模式只在搜索框右侧提供扫码按钮，扫描结果填入同一搜索框并筛选，手工搜索仍可用。未选岗继续禁用搜索和扫码；离页、换账号或换岗后丢弃旧相机结果。

## Phase 10：第一版真实集成续作
用户确认：先完成源码与测试环境业务闭环，随后做真机包；当前界面作为第一版基线。本阶段逐步补齐客户端契约与服务端能力，不重写无关系统。以下验收覆盖前文仅交付骨架的范围限制；生产操作和真实数据库写入仍需核实目标与授权。

- **FR-024**：申请单起终点候选集合独立于 Identity.posts。前者仅用于填写当前申请人有权申请的路线，后者只表示本人被授权执行的安检岗位；普通员工无安检岗位仍可提交合法申请。真实候选加载失败不能回退至演示或执行岗位；切换账号丢弃旧请求结果。
- **FR-025**：现场单据查询须显式提交已选岗位，服务端按当前身份、岗位和可执行状态裁定结果；客户端保留实时内存搜索，不在每次输入时请求后端。不得仅由客户端过滤服务器返回的所有园区单据。
- **FR-026**：第一版真实集成的完成证据必须包含测试环境身份认证、物品申请/审批/出发/到达与厂牌核验/进出及持久记录。领域单元测试、Mock HTTP 和演示验证单独记录，不能代替该证据。测试网关、授权/岗位来源、数据库基线、厂牌编码及刷卡证明来源未核实时，依赖能力保持待联调，不假设兼容。

本阶段先执行无外部环境依赖的 FR-024/025 客户端改造；身份、持久化和真实凭证适配以源码调查与测试环境事实继续设计。已向用户询问测试网关、配置读取位置和脱敏厂牌二维码。

- **FR-027**：平台服务提供独立保密物品领域规则，不改变旧 OA 放行或供应商预约状态。新单按 pending→approved/rejected、approved→transporting、transporting→completed 流转；审批必须是当前指派审批人且具有审批权限，禁止自批。现场人员必须有执行权限并被授权到对应起点/终点；出发到达均须服务端确认安检人刷卡，人工押运另须有效押运人刷卡证明，定位锁编号按字符串核验，到达不得更换方式或锁号。规则拒绝过期/错单/错岗/错动作的卡证、非法状态、空驳回意见与重复封条。此纯规则层不处理持久化事务或签发凭证，不构成真实放行接口。


### 用户对人员范围的最终澄清
供应商人员不登录 App，仅通过 H5 入厂申请办理入厂。App 内供应商模块是安检工作人员使用的厂牌核验/进出登记入口。App 账号范围是正式员工及需要使用客户端的外包／派遣工作人员，不能将供应商访客台账作为外包工作人员登录身份或据此新增供应商密码体系。

## Phase 11：供应商后端规则与工作人员认证准备
- **FR-028**：供应商服务端规则只接收由真实适配层查询得到的厂牌、人员、单位、入厂审批、有效期与区域快照。核验要求操作人有供应商执行权限及当前岗位授权，岗位对应区域在有效入厂资格内；无效或过期资格不得进入或离开普通登记流程。核验结果绑定操作人、岗位、厂牌、入厂申请、区域与人员在内状态版本，短时有效。每次明确登记进入/离开时，必须用当前资格再次核验，拒绝重复方向、旧版本、过期或不匹配的核验，并产生独立不可变事件。规则单测不能替代凭证查询、数据库事务或真实联调。
- **FR-029**：用户已选择新建本任务独立本机测试环境。容器、端口、数据卷和schema须明确归属本任务，不能复用其他任务或生产配置；本机凭据随机生成并保存在被忽略、限制读取权限的本地文件，不进入日志和版本控制。首先验证独立Oracle的健康及schema基线；第三方DHR等系统不建立本地数据库替身。
- **FR-030**：新增服务端显式工号密码认证能力，供后续统一会话入口使用；不依赖当前Servlet/OAuth查询参数，新内部凭据调用使用POST JSON，拒绝仅凭成功状态但结果为false的响应。新路径不得使用旧UserDetails缓存绕过本次密码验证，仍执行锁定、账号状态及既有强密码策略。原OAuth一参数入口与旧内部GET保持兼容；本增量不签发客户端会话、不推断人员来源或执行岗位。

  新路径必须覆盖已有账号的外包/派遣工作人员，不能依赖旧OAuth后续Provider才校验密码，也不能被既有测试成功分支绕过。JSON语法或正文校验失败须使用泛化错误，不回显或记录带凭据的解析异常。
- **FR-031**：物品放行的创建、审批、出区与到达必须通过真实Oracle仓储调用既有领域规则；单据快照、追加事件和命令幂等结果在同一事务提交，失败全部回滚。并发相同版本最多一方成功；同一操作人/作用域/幂等键的相同请求返回当次原结果，不同请求拒绝，权限撤销不能因幂等命中被绕过。首批实测只初始化本任务独立本机schema，不等于真实身份/设备/HTTP闭环。
- **FR-032**：供应商核验与进出使用真实Oracle持久化；按人员/区域保存状态，核验仅能消耗一次，状态CAS、消耗核验、追加事件及幂等原回复须在同一事务内提交。缺少人员区域初始状态时明确拒绝，不能默认推断在外；当前资格与岗位每次登记重验。测试只明确初始化合成人员，不据此伪造真实厂牌或第三方资格来源。

## Phase 13：入厂访客记录与供应商通行接口
用户确认供应商资料来自已有H5入厂申请；厂牌二维码使用访客记录ID，禁止使用一次性、可能重复的6位预约码。裕同认证联调后置。

- **FR-033**：厂牌使用每名访客的 `SMT_ADMITTANCE_FELLOW.ID` 十进制字符串，关联 `VISITOR_ID` 对应的入厂申请；主申请ID不能代替多名人员的ID。扫码不按短信码查询，不自动回退其他记录域。ID接受规范正Long字符串，不能以位数代替记录来源判断；合法短人员ID不属于短信预约码。服务端从现有申请/人员数据取得姓名、照片、公司、被访人、有效期、状态和区域；不要求先成为长期供应商台账人员。记录ID不是通行授权，仍核工作人员权限、岗位园区、申请已通过/已到达状态、时间及明确区域映射。没有个人电话时不把申请联系人电话冒充个人电话。
- **FR-034**：首次登记可以没有历史区域状态；新接口在真实资格与岗位检查通过后建立显式 `UNKNOWN` 状态，核验后由安检明确选择进入或离开，首次事件才确定在内/在外。不得默认在外，不改变已有状态，不允许缺资格建状态；并发首次核验或登记仍只能生成一致状态及单次事件。此条对FR-032的缺基线拒绝作有界补充，旧严格仓储入口保持原行为。
- **FR-035**：供应商HTTP接口对接既有Oracle仓储与入厂申请读取，不使用演示数据。身份只取已认证的服务端SmartUser，执行/查询权限和岗位权限分别校验，并与园区集合相交；岗位及入厂区域映射由服务端配置，默认不开启接口、无默认岗位授权。登记锁定同一Oracle中的申请/人员记录，重读当时资格并持锁至通行事务结束；锁等待后按实际时间判断失效。查询只返回本人有权查看岗位的事件。当前可以测试认证上下文下的业务接口，DHR登录、网关路由和真机结果继续单独验收。

Phase13评审修正：维护中H5仅接受通过18位身份证校验位规则的人员证件，payload显式提交certType=0。兼容已存历史null时，只有通过同一身份证校验才按类型0规范化，拒绝不能确认的空类型；明确类型仅接受系统0–5枚举。历史null与后续显式0必须保持同一人员身份与区域状态，不回填真实数据。

## Phase 14：App 专用接口闭环

- **FR-036**：App 会话必须采用统一网关的 JSON `POST /api/v1/sessions` 签发 token，再由 `GET /api/v1/me` 根据 Bearer token 和当前人员主数据返回身份、权限及岗位。不得修改旧 OAuth token、H5 或后台登录契约；App 不持有 OAuth client secret。正式、外协和派遣人员根据已同步员工及组织关系映射，离职、停用和未知用工类型失败关闭；供应商人员不具有 App 登录入口。
- **FR-037**：物品放行必须使用新增 `/api/v1/item-passes` 接口及独立持久化表，不读写旧 OA 单据。创建、审批、执行、岗位候选和查询均由服务端重判 token、园区、岗位、状态及幂等键。押运人提交的工牌号必须由服务端重新查询有效工作人员，安检人员不能自任押运人；定位锁编号与出发方式由服务端约束。首版扫码输入不等同读卡器签名，读卡设备可通过同一后端卡证适配器另行接入。
- **FR-038**：所有 App 业务端点默认关闭且不提供默认岗位、审批人或账号权限。供应商厂牌端点使用 `POST /api/v1/visitor-checks`、`GET/POST /api/v1/visitor-passes`，复用 H5 已存入厂申请与人员记录 ID，登记前重读当前员工身份。真实客户端仅配置统一 HTTPS API 网关基地址；网关实际路由、OAuth client 登记、DHR/外协/派遣账号、照片服务与设备必须独立验收，不能以 MockMvc 或本地 Docker Oracle 代替。

## Phase 15：统一登录与隔离本机演示闭环

- **FR-039**：App 对外只提供 `POST /api/v1/sessions` 一个工号密码会话入口，客户端不得选择或提交人员来源。服务端先从智慧园区人员主数据裁定来源：外包／派遣人员使用系统内账户凭据，正式员工使用可替换的 DHR 凭据适配器；身份、状态、园区与权限仍由服务端最终裁定。未知、停用或来源无法确认的人员失败关闭。
- **FR-040**：DHR 凭据适配器的稳定边界为“工号、密码 → 通过或拒绝”，不改变 App API 或令牌格式。本机演示仅启用明确命名的本地模拟适配器；真实 DHR 地址、鉴权方式、字段和证书由用户提供后以独立配置接入，不能将密码拼入 URL、日志、缓存或数据库。
- **FR-041**：补齐模块目录 `GET /api/v1/me/apps` 与物品放行详情 `GET /api/v1/item-passes/{id}`；模块元数据只能与客户端本地白名单取交集，详情继续按服务端可见范围裁定。旧 OA、H5、后台、OAuth 和访客申请接口不得改动或重定向。
- **FR-042**：本机演示使用独立的 `smart-app-demo` Docker 项目、网络、卷、Oracle schema、Nacos namespace 和虚构数据，只启动 Nacos、Redis、Oracle、UPMS、认证、平台与网关。演示数据必须标示虚构且不连接 DHR；供应商资格仍从同一平台访客表查询，二维码只使用 `SMT_ADMITTANCE_FELLOW.ID`。
- **FR-043**：本机 H5 演示可通过受限的本机运行配置调用回环网关；默认和生产 App 构建仍要求 HTTPS，不提供任意服务地址编辑能力。网关 CORS 仅对本机演示源开放，不能扩大通用跨域策略。
