# Research: 入厂申请区域并发判重

## Decision 1: 使用持久化的证件号锁锚点

- **Decision**: 为每个证件号创建或锁定一条不含明文证件号的协调记录；同一申请内的唯一证件号按稳定顺序取得锁，再进行判重与保存。
- **Rationale**: 当前保存流程在事务中先调用判重、后保存申请和随行人员。两笔首发申请可同时读到“无冲突”，所以仅改查询条件不能满足“并发最多一方成功”。稳定排序避免两份多人员申请以相反顺序锁定证件号而死锁。已存在锚点行的 `FOR UPDATE WAIT 10` 有等待上界；两笔首次创建同一锚点时，Oracle 唯一键竞争会先等待先行事务结束，之后成功创建或转为重试取锁，因而不产生双成功，但其实际等待上界必须由 Oracle 验收确认。
- **Alternatives considered**: 只锁已有申请行无法覆盖“尚无记录”的首发竞态；提交前检查无法保留锁到正式提交；全局锁会让无关人员彼此阻塞。

## Decision 2: 区域按逗号边界精确比较

- **Decision**: 每个待提交区域与已有申请的区域串使用逗号边界比较；任意一项相同即区域重叠。
- **Rationale**: 新申请保存时将区域 ID 用逗号连接；直接子串匹配会把 `1` 与 `11` 误判为同一地区。
- **Alternatives considered**: 精确比较整个串会遗漏多选重叠；将区域拆成新表会扩大数据迁移和现网范围。

## Decision 3: 区域未知按保守策略冲突

- **Decision**: 有效历史申请区域为空或格式异常时，及当前兼容提交没有区域时，只要证件号与时间重叠就视为冲突。
- **Rationale**: 用户已明确选择“安全优先”；缺失区域不能成为重复通行授权的绕过条件。
- **Alternatives considered**: 忽略区域未知记录会漏拦；猜测其所属新厂/老厂会引入没有证据的数据修复。

## Decision 4: 将 Oracle 并发验证作为发布前门槛

- **Decision**: 代码级验证覆盖锁协议调用与绑定 SQL；最终上线前必须在隔离 Oracle 测试库运行至少 20 轮双事务竞争。
- **Rationale**: Mock 不能证明 Oracle 唯一键竞争与 `FOR UPDATE` 等待语义；本地工作区没有可确认的测试 Oracle 状态。
- **Alternatives considered**: 仅以单元测试宣布并发安全会超过其证据能力。
