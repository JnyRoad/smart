# Feature Specification: 入厂申请区域并发判重

**Feature**: `002-admittance-duplicate-guard`
**Created**: 2026-09-02
**Status**: 代码与 SQL 契约已验证，待隔离 Oracle 并发验收
**Input**: 优化蓝图 2.7：按新厂/老厂区域判重，将主申请人与随行人员纳入判重，并确保并发提交不能同时成功。

## Clarifications

### Session 2026-09-02

- Q: 已存在且仍有效、但缺少或格式错误区域信息的历史申请应如何参与判重？ → A: 采用保守策略：同证件号且时间重叠即冲突。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同区域的人员重复申请被阻止 (Priority: P1)

园区工作人员提交入厂申请时，系统核验主申请人和每位随行人员，避免同一证件号在重叠时段进入相同区域的多张有效申请。

**Why this priority**: 同一人员获得重复有效通行授权会造成门禁与现场管理风险。

**Independent Test**: 准备一张含有效人员记录的申请；对同一证件号、重叠时段和有共同区域的新申请提交，确认提交被拒绝，并指出冲突人员与时间段。

**Acceptance Scenarios**:

1. **Given** 现有有效申请的主申请人与新申请主申请人证件号相同且区域、时间均重叠，**When** 提交新申请，**Then** 系统拒绝提交。
2. **Given** 现有有效申请含一位随行人员，且该证件号出现在新申请的主申请人或任一随行人员中，**When** 区域、时间均重叠并提交，**Then** 系统拒绝提交。
3. **Given** 同一证件号的两张申请时间仅在端点相接而没有重叠，**When** 提交后者，**Then** 系统允许提交。

---

### User Story 2 - 跨区域的申请可以共存 (Priority: P1)

现场人员可以在同一时间段分别申请互不相交的新厂/老厂区域，不会被不相关区域阻止。

**Why this priority**: 新厂与老厂区域对应独立的门岗与权限，不能因证件号相同而误拦截正常业务。

**Independent Test**: 准备一张仅含新厂区域的有效申请；为相同证件号、相同时间提交仅含老厂区域的申请，确认提交成功。

**Acceptance Scenarios**:

1. **Given** 两张申请的证件号和时间段相同，但区域没有交集，**When** 提交后者，**Then** 系统允许提交。
2. **Given** 一张申请选择多个区域，且另一张申请至少选择其中一个相同区域，**When** 时间段重叠，**Then** 系统拒绝提交。

---

### User Story 3 - 并发提交只允许一方成功 (Priority: P1)

两位操作员或同一用户的两个请求同时提交相同证件号、重叠时段和相交区域的申请时，系统只接受其中一份。

**Why this priority**: 提交前检查不能替代提交时的原子校验；必须消除“两个请求都先查到无冲突再同时写入”的竞态。

**Independent Test**: 让两个独立事务在同一时刻提交同一人员、相同区域和重叠时间段的申请，确认恰好一个提交成功，另一个得到重复申请或“申请处理中”的业务拒绝，且最终只有一张有效申请。

**Acceptance Scenarios**:

1. **Given** 两个相同的冲突申请同时提交，**When** 两个请求完成，**Then** 恰好一个成功、一个被拒绝。
2. **Given** 同一批申请含多位人员，**When** 并发请求的人员集合有任意一个共同证件号，**Then** 不会因锁定顺序不同而互相永久等待，且仍最多一方成功。
3. **Given** 用户先执行提交前检查、之后才真正提交，**When** 期间另一笔冲突申请已成功，**Then** 最终提交仍被拒绝；提交前检查只提供即时提示。

### Edge Cases

- 任何主申请人或随行人员没有可用于判重的证件号时，系统拒绝该申请并明确指出对应人员，不能静默跳过。
- 已拒绝和已作废的申请不参与判重。
- 同一申请内重复出现相同证件号时，系统仍应稳定完成判重，不能因重复锁定造成死锁或异常。
- 区域 ID 为 `1` 时不能与 `11` 视为同一区域。
- 已存在且仍有效、但缺少或包含无效区域信息的历史申请，按保守策略与同证件号、时间重叠的任意新申请冲突，避免历史缺失信息绕过门禁风险。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在正式提交入厂申请时，对主申请人与所有随行人员逐一执行重复申请校验。
- **FR-002**: 对同一证件号，系统必须仅在预约时间重叠且申请区域存在至少一个相同区域时阻止提交。
- **FR-003**: 系统必须允许证件号和预约时间相同、但申请区域完全不相交的申请共存。
- **FR-004**: 系统必须将已拒绝和已作废申请排除在重复申请判断之外。
- **FR-005**: 对任意一组同时提交的冲突申请，系统必须最多接受一份；其余请求必须得到可识别的重复申请或处理中业务结果，而不能悄然写入第二份有效申请。
- **FR-006**: 系统必须在同一事务中完成并发协调、重复申请判断和申请保存；单独的提交前检查不得被视为最终许可。
- **FR-007**: 系统必须要求主申请人与所有随行人员提供非空证件号，才能提交需要判重的入厂申请。
- **FR-008**: 系统必须保持现有提交请求字段与页面流程兼容，不要求用户新增操作。
- **FR-009**: 系统必须将区域作为完整的离散区域值比较，不得使用会把部分数字误认为相同区域的模糊比较。
- **FR-010**: 系统必须保持现有“开始时间等于另一申请结束时间不冲突”的时间边界语义。
- **FR-011**: 对仍有效但缺少或包含无效区域信息的历史申请，系统必须在证件号和预约时间重叠时拒绝新申请，不得因区域信息缺失放行。
- **FR-012**: 对当前提交申请中无法识别区域的情况，系统必须采用与历史区域缺失记录相同的保守策略：同证件号且预约时间重叠即拒绝，不得绕过判重。

### Key Entities *(include if feature involves data)*

- **入厂申请**: 主业务记录；其状态、预约时间和申请区域决定是否参与判重。
- **申请人员**: 主申请人与随行人员的统称；每人以证件号作为判重身份。
- **区域**: 申请选择的离散通行区域；只有两个申请共享至少一个区域才构成区域重叠。
- **并发协调记录**: 用于让同一证件号的同时提交按顺序完成判断的内部记录，不向最终用户展示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在覆盖主申请人、随行人员和角色交叉的所有证件号冲突场景中，100% 拒绝同区域且时间重叠的重复申请。
- **SC-002**: 在区域完全不相交的测试场景中，100% 允许相同证件号和重叠时间的申请提交。
- **SC-003**: 在至少 20 轮双请求并发测试中，每轮恰好一份冲突申请成功，且最终每轮仅保留一张有效申请。
- **SC-004**: 区域值存在数字前缀关系的测试中，0 次将不相同区域误判为相同。
- **SC-005**: 已拒绝、已作废和时间端点相接的既有允许场景保持通过。

## Assumptions

- 当前入厂申请的区域选择代表离散区域，且新提交申请会携带可验证的区域选择。
- 已确认的业务规则是：新厂与老厂的无交集区域可以并存；任意一个共同区域即可构成冲突。
- 历史有效申请若无法可靠识别区域，优先避免重复授权风险，不享受跨区域并存规则。
- 当前提交申请若使用现有兼容路径而未提供区域，同样按区域未知处理；该兼容路径不享受跨区域并存规则。
- 并发保证针对正式提交入口；提交前检查仅改善交互反馈，不能预留或占用提交资格。
- 已存在锁行的行锁等待由 `FOR UPDATE WAIT 10` 限制；首次创建同一锁行的唯一键竞争会等待先行事务完成后再重试取锁，实际等待上界需由隔离 Oracle 验收确认。
- 本功能的数据库对象变更将作为单独、可回滚的发布步骤评审；本次实现不会自行执行任何真实环境 DDL 或数据写入。
